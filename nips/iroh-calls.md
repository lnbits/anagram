# Nostr + Iroh calls

Nostr authenticates peers and exchanges connection details. Iroh carries encrypted audio, video and screen streams. These are Anagram extensions, not assigned Nostr standards.

## Signalling

- Call and room controls use the conversation's selected encryption. A double-ratchet conversation sends every `kind:21117` control through its authenticated session. Initialization or delivery failure cannot fall back to NIP-17.
- Legacy NIP-17 controls attempt delivery to configured app relays and any known recipient inboxes. Known delivery routes are used while inbox metadata refreshes in the background. If delivery fails or no route is known, discovery has a bounded 1.5-second fallback wait. A single relay acknowledgement is sufficient; other publish attempts continue without delaying negotiation.
- For NIP-17, the unsigned `kind:21117` rumor travels inside a NIP-44 `kind:13` seal and NIP-59 `kind:1059` gift wrap, with one intended `p` recipient. The rumor author must match the seal signer. Private publication uses separate send-only connections with fresh anonymous authentication, never the account's receiving pool.
- JSON uses `protocol: "anagram/iroh-call/1"`, UUID `callId`, `action` (`invite`, `ringing`, `accept`, `end`), `mode` (`audio`, `video`) and ISO `expiresAt`.
- Invites and accepts include `address: { id, relayUrl }` and `mimeType`. End controls include a reason. Signals expire within 60 seconds; future timestamps beyond 10 seconds are rejected.
- Each call creates fresh Iroh endpoints. Peers accept only the endpoint authenticated by the other's Nostr signal, exchange the call UUID over ALPN `anagram/call/1`, then exchange ready frames before sending media.

## Media

- QUIC/TLS protects transport, including through Iroh relays. Frames have a big-endian 32-bit length prefix and a 1 MiB maximum.
- Frame types: `0` audio, `1` heartbeat, `2` ready, `3` video, `4` audio reset, `5` camera off/on, `6` screen video, `7` screen off/on, `8` microphone mute state. State frames carry one byte (`0` or `1`).
- Both peers negotiate `mediaVersion: 2` for separate WebM Opus audio and VP8 video. Screen and mute-state frames additionally require mutual `screenSupported` and `muteStateSupported`. Version 1 uses combined WebM media.
- Heartbeats run every 3 seconds; 15 seconds without a frame ends the connection. Media never travels through Nostr relays.
- Peers advertising `transportVersion: 2` use ALPN `anagram/call/2` with four separately ordered bidirectional streams: control, audio (types `0`, `4`), camera (`3`, `5`) and screen (`6`, `7`). Each stream confirms the call UUID before use. Control and audio have higher send priorities; receivers retain at most one pending frame per stream and deliver ready before media. Otherwise the original single-stream transport is used.
- Legacy WebM sends combine chunks already waiting into one ordered frame, avoiding one native IPC round trip per accumulated chunk. No batching timer or additional buffering delay is introduced; each frame, including its lane marker, stays within the 1 MiB limit. Legacy audio keeps its 200 ms playback target and seeks only beyond 450 ms of buffered lag, leaving room for burst arrivals without repeated seeks.
- Video send queues older than 1.5 seconds stop that video stream rather than discard dependent WebM chunks. Camera encoder/capture failures and video decoder failures leave audio connected. A failed decoder discards further chunks until the sender explicitly starts a fresh stream.

### Negotiated packet media

- Optional `packetAudioVersion: 1` and `packetVideoVersion: 1` capabilities are independent of `mediaVersion: 2`. Both endpoints must advertise a capability before using it. Clients without it retain the existing WebM format, including combined media for version 1. Audio codec/AudioWorklet initialization and VP8 encoder/decoder capability checks happen before advertising support.
- Native Linux currently negotiates WebM audio: WebKitGTK 2.52 can exceed its realtime AudioWorklet CPU limit and lose the renderer under group-call load. This selection applies only to installed Linux clients, not Linux browsers or Android. Other supported engines retain packet audio. WebM retains the existing 200 ms playback target and relay-only encryption.
- Packet audio uses mono 48 kHz Opus, 960 samples (20 ms), 32 kbps, with in-band FEC enabled. Encoding and decoding run in a dedicated worker; the audio render thread only moves PCM. A room shares its microphone encoder, while each incoming stream has its own decoder and jitter buffer.
- Audio datagrams are at most 1,100 bytes: type `9`, version `1`, a big-endian uint32 generation, uint32 sequence, uint32 sample timestamp, then Opus. Sequence/timestamps wrap modulo 2^32. Generations increment when capture restarts; previous generations are discarded. Reliable audio lane type `9` is available for transports without the datagram methods. Ready/reset/mute/heartbeat controls remain reliable.
- The audio jitter target adapts from 40 to 160 ms, with rapid increases and gradual decreases. A missing frame uses the following packet's FEC when available, otherwise Opus concealment; prolonged absence re-buffers. The packet map, worker ports and per-peer sends are bounded. A backlog is trimmed toward live speech rather than replayed in full. Iroh's audio datagram send buffer is limited to 2,200 bytes. WebSocket/TCP relay stalls can still cause audible interruptions; datagrams do not remove TCP head-of-line blocking.
- Packet VP8 retains camera/screen lanes and state controls. After stripping the lane type byte, its header is version `1`, keyframe flag (`0`/`1`), and a big-endian float64 timestamp in microseconds, followed by one encoded VP8 frame. Timestamps must be nonnegative safe integers. The maximum frame is 512 KiB. Receivers bound their decode queue, require a keyframe after overload, and close every decoded `VideoFrame`. Canvas playback requests frames explicitly when supported; engines without manual frame requests use automatic capture capped at 24 fps. Audio never waits for video synchronization.
- Packet video shares encoders for identical source/bitrate profiles, bounds each peer to one outstanding frame, and requests frequent recovery keyframes. Sustained send pressure reduces the shared profile bitrate, with gradual recovery. Per-peer queues do not block each other. Legacy WebM still preserves its ordered initialization/segments and reconnects after an audio send queue exceeds 1.5 seconds.
- Packet video requires working VP8 WebCodecs encoder/decoder support. Capture prefers a bounded `MediaStreamTrackProcessor`; engines such as WebKit without that API use one muted video element and an on-demand canvas frame, capped at 1920×1080. Both capture paths bound retained frames, and encoding is skipped when every peer is busy. Encoders share the captured track and release frames, canvas storage and source clones when stopped. The element capture path detaches and clears its player, then weakly retains one idle player per source track for reconnection; this preserves WebKit playback permission without retaining a live capture. Cleanup is idempotent. Engines without either capture API or VP8 codec support, and older peers, retain WebM video.
- Decoder diagnostics are local counters only (buffer target, jitter, late/duplicate/concealed frames). Transport snapshots report selected-path RTT, path count and whether all paths are relays. They contain no media, account keys or IP addresses and are discarded at call end.

### Native transport and relay privacy

- Installed clients use the same Rust transport through a main-window-only native bridge; browsers use the bundled WASM build. Native endpoints explicitly clear IP transports. Browser WASM has no IP transport. Both use fresh identities, authenticated peer/call binding and encrypted QUIC through the configured Iroh relays. No direct fallback or public address lookup is enabled.
- Native handles are bounded and released at hangup, window destruction or a new WebView client session after reload. Relay URLs require HTTPS. Desktop/iOS verify relay certificates using platform trust; Android uses Iroh's verified embedded Mozilla roots. Certificate verification is never disabled in application code.
- Native audio receives at most four recent datagrams per IPC response, with a bounded drain of the transport backlog. Two outgoing audio datagrams may await acknowledgement, with one latest packet pending. This avoids making a 20 ms audio packet wait for an entire WebView IPC round trip, without allowing an unbounded native/JavaScript queue. The network packet format is unchanged.

## Connection recovery

- Both peers must advertise `reconnectSupported: true`. Existing clients retain the original failure behavior.
- After an established connection fails, the original caller coordinates recovery using authenticated `reconnect` controls with `reconnectAttempt` (a monotonically increasing positive safe integer). The callee can send the same action to request recovery; it cannot initiate a new call this way.
- Each attempt creates fresh endpoints. The caller sends its new address; the callee starts accepting and returns `accept` with the matching attempt and its new address. Controls retain the original peer, call UUID, mode and group-session bindings. Duplicate/stale attempts do not restart a healthy connection.
- Recovery retries controls every two seconds, permits a second attempt after ten seconds, and ends after twenty seconds without recovery. There are at most two attempts per interruption; a later interruption gets a new bounded recovery window while attempt numbers continue increasing. Hangup, decline and other deliberate remote endings remain final.
- Capture, mute state and original start time survive recovery. Decoders and recorders restart together on the new connection; callbacks from a previous connection cannot affect its replacement.
- Muting stops a legacy separate-audio recorder without releasing the microphone track or stopping video. Unmuting resets that audio lane before starting a fresh recorder. Combined legacy audio/video keeps recording so muting cannot stop its camera. WebKit can stop producing chunks or change timestamps after a track is disabled, including on connections that did not reconnect. The reset preserves video and microphone capture. Packet audio keeps its continuous sequence and does not reset on mute toggles.

## Group calls

- Links contain a room UUID, host pubkey, random 256-bit admission secret, inbox relay hints and expiry. The capability stays in the URL fragment; it contains no Iroh keys.
- Recipient-only controls use `anagram/iroh-room/1`: `join`, `roster`, `signal`, `leave`, `closed`, `rejected`. The host admits members and signs monotonically increasing roster revisions through the same encrypted envelopes.
- Each participant chooses their own display name before creating or joining and can edit it during the call. Names travel in the member `name` field of join and roster controls. In-call edits increment an optional nonnegative `nameRevision` (missing means zero). Guests resend their own authenticated join with the same session; the host accepts only a newer name revision for that member, then broadcasts a new roster revision. Name changes preserve existing media connections. Older hosts ignore guest name edits until everyone updates. Custom CSS is a local rendering preference and never enters signalling.
- Each join has a fresh session UUID. Pair signals bind both sessions; the lower pubkey initiates. Current members form a full mesh of separately authenticated Iroh connections.
- At four or more participants, the room divides a 900 kbps camera budget and 1.5 Mbps screen budget across recipients, at 15 fps and 5 fps respectively. Smaller rooms retain 600 kbps/24 fps camera and 1.5 Mbps/15 fps screen targets per peer. Existing streams restart with fresh headers when the preset changes. Audio has separate transport priority and queues.
- Reconnecting peers stay in the roster until recovery succeeds or its deadline expires.
- Rooms allow six participants, expire within eight hours and end when the host leaves. Possession of the link grants admission, subject to host checks.

## Call history

Optional encrypted `kind:14` summaries carry `anagram-call`, version `1`, call UUID, mode, end reason, duration in seconds and an active flag (`0` or `1`). They contain no media or endpoint addresses and never initiate a call.

## Validation

- Run `npm run quality:all`, `npm run test:unit`, and `npm run build`. Verify rebuilt browser transport assets with `npm run verify:iroh`.
- Browser media checks: `npm run test:e2e:local -- --browser chromium e2e/call-packet-audio.spec.ts e2e/call-packet-video.spec.ts e2e/call-playback.spec.ts e2e/call-ui.spec.ts e2e/mobile-call-audio.spec.ts e2e/ios-layout.spec.ts`. The call workflow repeats these on Firefox and macOS WebKit. Unsupported packet-video codecs are explicitly skipped; legacy playback is tested separately.
- `node scripts/native-calls/run.mjs --browser` exercises the production call runtimes and an actual local TLS Iroh relay. `--linux` runs the Linux Tauri executable; the native-call workflow covers macOS and Windows. These probes use generated audio/video, check decoded audio and changing video pictures, mute, forced reconnection, relay-only paths and hangup, and save results under `.artifacts/native-calls/`. The Linux group probe runs each participant in its own app with an 800×600 window and isolated application data. Its local test server coordinates signalling and measurement barriers; media still uses the production encrypted Iroh transport. Provide a virtual display large enough for the tiled windows (1600×1200 for four participants). They do not validate physical microphones, earpieces, cameras, Bluetooth or cellular handovers.
- The browser probe simulates six participants. The native default is four participants; set `ANAGRAM_CALL_TEST_PARTICIPANTS=6` for a six-person room. macOS and Windows still simulate all participants in one WebView, making this a heavier stress case there. A real participant in a six-person room runs five remote decoders. Stress failures must be reported separately, not counted as passing native-call validation.
- Run sustained media probes separately from other browser suites so CPU contention from several simulated participants does not obscure playback failures. The iPhone application build/release workflow remains disabled; browser layout tests are not iPhone-device validation.
- Use `ANAGRAM_CALL_TEST_SCENARIO=direct`, `group`, or `legacy` to isolate a failing scenario; the default runs all three. Probe snapshots include active recording send counts and track state to distinguish capture stalls from transport or playback failures.
